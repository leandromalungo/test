# MASTER PROMPT — AGRICULTURAL PARAMETRIC INSURANCE PLATFORM

## 1. PROJECT OVERVIEW

Build a complete, functional MVP of a modern **Agricultural Parametric Insurance Platform** designed for the Angolan insurance market.

The platform must allow small and medium-sized farmers to access agricultural insurance against climate risks, particularly:
- Drought.
- Excessive rainfall.

The system must use measurable, externally verifiable meteorological data to evaluate climate events, calculate insurance premiums, determine policy triggers and calculate indemnity payments automatically.

The platform must be designed as a real insurance management system, not just a visual prototype.

**Core principle:** Every important operation must be executable, traceable, explainable and auditable.

Build the entire application using Next.js, TypeScript and Supabase, with all business logic implemented through secure APIs inside the Next.js application.

## 3. APPLICATION ARCHITECTURE

Use a modular full-stack architecture.

The frontend must never communicate directly with external climate providers or execute sensitive insurance calculations.

All important operations must go through Next.js APIs.

Architecture:

Frontend (Next.js)
↓
Next.js API Routes
↓
Business Logic Services
↓
Supabase PostgreSQL / External APIs

Organize the project into independent modules:

1. Authentication and authorization.
2. User and customer management.
3. Agricultural property management.
4. Insurance products.
5. Insurance simulation.
6. Risk assessment.
7. Premium calculation.
8. Policy management.

11. Event detection.
12. Indemnity calculation.
13. Payment simulation.
14. Notifications.

## 7. INSURANCE SIMULATOR

This is one of the most important features.

Build a complete interactive insurance simulator.

The farmer must be able to:
1. Select an agricultural location.
2. Select the crop.
3. Select the agricultural campaign.
4. Select insurance coverage against drought or excessive rainfall.
5. Define the insured capital.
6. View the climate indicator.
7. View the coverage thresholds.
8. View the estimated premium.
9. View the possible indemnity.
10. Review the insurance conditions.

The simulator must retrieve product configurations from Supabase.

Do not hardcode insurance products in frontend components.

### Premium calculation

Implement a configurable premium engine.

Example:

Premium = Insured Capital × Premium Rate

The premium rate must be configurable according to:
- Crop.
- Geographical location.
- Historical climate risk.
- Insurance period.
- Coverage type.
- Risk classification.

For the MVP, use configurable actuarial assumptions rather than claiming to have a validated actuarial model.

Show the calculation breakdown to the user.

## 9. CLIMATE DATA INTEGRATION

This module is critical.

Build an independent climate data integration layer.

Create a provider adapter architecture.

### Initial providers

Implement adapters for:
1. Open-Meteo Historical Weather API using ERA5/ERA5-Land data.
2. NASA POWER Daily API.
3. CHIRPS, where an accessible and documented integration is available.
4. INAMET and GGPEN as future institutional integration adapters.
5. Copernicus as an additional integration option.

Do not invent APIs, credentials or institutional integrations.

Use the actual documented API endpoints and parameters.

For the MVP, prioritize at least one working external provider and a second source for comparison.

### Data collected

For every observation, record:
- Provider.
- Geographic coordinates.
- Observation date.
- Precipitation amount.
- Measurement unit.
- Retrieval timestamp.
- Source URL or endpoint.
- Data resolution, when available.
- Data quality status.
- Original response or a reproducible reference to it.
- Data validation results.

Normalize precipitation values to millimetres.

### Data validation

Implement validation for:
- Missing observations.
- Invalid values.
- Incomplete periods.
- Delayed data.
- Duplicate observations.
- Incorrect units.
- Geographic mismatches.
- Significant differences between sources.

Never treat missing data as zero rainfall.

### Source comparison

Compare observations from the primary source and confirmation source.

Allow configurable disagreement thresholds.

When the data quality requirements are not satisfied:
- Do not activate an automatic indemnity.
- Create an exception.
- Notify the operator.
- Preserve the evidence.
- Allow manual investigation.

The system must distinguish between actual external data and simulated demonstration data.

Never present mock data as real meteorological observations.

## 11. EVENT DETECTION AND PARAMETRIC TRIGGERS

Create a configurable trigger engine.

Support two initial insurance scenarios.

### Scenario A: Drought

The system calculates accumulated precipitation over a predefined period.

If precipitation falls below the contractual threshold, the event may activate.

### Scenario B: Excessive rainfall

The system calculates accumulated precipitation over a predefined period.

If precipitation exceeds the contractual threshold, the event may activate.

The thresholds must be defined in the insurance product and copied into the policy at subscription time.

Never change an existing policy's contractual parameters when a manager modifies a product.

Use versioned insurance configurations.

### Event lifecycle

Implement the following statuses:
- Monitoring.
- Potential event.
- Data validation pending.
- Trigger activated.
- Trigger not activated.
- Manual review.
- Indemnity calculated.
- Payment pending.
- Paid.
- Rejected.
- Exception.

Every event must contain an explanation of the rule applied.

## 12. INDEMNITY CALCULATION ENGINE

Implement a separate indemnity calculation service.

Use configurable severity bands.

Example:

| Precipitation condition | Payout percentage |
|---|---:|
| Within normal range | 0% |
| Moderate deviation | 25% |
| Significant deviation | 50% |
| Severe deviation | 75% |
| Extreme deviation | 100% |

These values are illustrative and must be configurable.

Formula:

Indemnity = Insured Capital × Payout Percentage

The backend must return:
- Insured capital.
- Observed precipitation.
- Contractual threshold.
- Severity classification.
- Applicable payout percentage.
- Calculated indemnity.
- Calculation explanation.
- Source evidence.
- Calculation timestamp.

Implement validation to ensure that the indemnity never exceeds the insured capital or contractual maximum.

Use Decimal.js for financial arithmetic.

Examples:
- Customer registration.
- Farm registration.
- Product configuration.
- Premium calculation.
- Policy creation.
- Climate data retrieval.
- Trigger activation.
- Indemnity calculation.
- Payment creation.
- Manual approval.
- Manual rejection.
- Configuration changes.

- User ID, when applicable.
- Action.
- Entity type.
- Entity ID.
- Timestamp.
- Previous state, when applicable.
- New state, when applicable.
- Relevant metadata.
- Operation result.

Audit records must not be editable through normal application interfaces.

### Security requirements
- Use Supabase Auth.
- Implement Row Level Security.
- Enforce role-based authorization on the server.
- Validate every API request.
- Protect sensitive operations.
- Prevent unauthorized access to other customers' policies.
- Never expose the Supabase service role key.
- Never store credentials in source code.
- Use environment variables.
- Avoid leaking sensitive information in logs.
- Implement rate limiting on sensitive endpoints where practical.
- Use secure error handling.
- Protect against duplicate payment and event processing.

Use database transactions and idempotency mechanisms where appropriate.

## 24. FINAL ACCEPTANCE CRITERIA

## 25. CODE ORGANIZATION, COMPONENTIZATION AND PORTUGUESE COMMENTS

This project must follow professional software engineering practices. **Do not concentrate large amounts of code, business logic, UI markup or multiple unrelated responsibilities in a single file.**

The application must be organized into small, reusable, independently understandable modules.

### Componentization rules

- Create separate React components for each meaningful interface element or functional section.
- Do not build entire pages as one large component.
- Keep page files focused on composing components and loading the data required by the page.
- Extract repeated interface patterns into reusable components.
- Separate layout components, form components, tables, charts, dialogs, navigation and status indicators.
- Split complex forms into smaller components or steps.
- Split complex dashboards into independent sections and widgets.
- Use shared components only when they represent genuinely reusable functionality.
- Avoid creating one generic component with dozens of unrelated conditions and props.
- Keep components focused on a single responsibility.
- Prefer composition over deeply nested conditional rendering.
- Keep component files reasonably small and readable. When a file becomes difficult to understand, maintain or test, split it into smaller modules.

### Separation of responsibilities

Maintain a clear separation between:

1. **Pages:** route-level composition and page orchestration.
2. **UI components:** visual elements and user interaction.
3. **Hooks:** reusable client-side state and interaction logic.
4. **API Route Handlers:** HTTP request handling, validation and response formatting.
5. **Services:** business rules and application use cases.
6. **Repositories/data access:** database queries and persistence logic, where this abstraction is useful.
7. **Schemas:** Zod validation schemas.
8. **Types:** shared TypeScript types and interfaces.
9. **Utilities:** small reusable helper functions.
10. **Configuration:** application settings and constants.

Do not put database queries, insurance calculations or complex business rules directly inside React components.

Do not put all business logic inside API route handlers.

Do not create unnecessarily large files containing multiple unrelated components, services, schemas or functions.
